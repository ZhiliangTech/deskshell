# 外联文案 · 中文

给从没听过这个项目的中国开发者。只干一件事：让他愿意花 30 分钟，并且知道第一步做什么。

---

## 用法

1. **第一句必须是关于他的。** 每段都以 `{为什么是他}` 开头——一句具体的、只有看过他项目才写得出来的话。写不出这句，这个人就还不是线索。
2. **每条都以 30 分钟动作结尾。** 只允许三种：跑 `doctor`、写一个 skill、认领一个 issue。不要用"有空看看"结尾。
3. **数字只从仓库里拿。** 可以说的：Node >= 22.18；协议 v0 冻结（8 种 action / 7 种断言 / 5 种 undo / 7 个 capability）；驱动接口 6 个必选方法 + 2 个可选；录制器 300ms 轮询、只抓左键。不说用户数、star、性能倍数、融资、合作方。
4. **不许吹。** Linux 没驱动、npm 还没发、录制器只抓左键——这些主动讲，讲了才有人信别的。
5. 替换 `{名字}`、`{项目}`、`{issue 链接}`、`{仓库地址}`。占位符没换干净就不要发。

一句话定位（一直用这句，别换花样）：**每个动作都必须可验证、可撤销、可审计；内核里没有模型。**

## 3. V2EX（分享创造节点）

### 标题（选一个，不要加"重磅""神器"）

1. `分享创造：给 AI 操作电脑加一层事务语义——每个动作要自证、能撤销、有日志`
2. `分享创造：我写了一个不会有"跑到一半悄悄失败"的桌面操作内核`
3. `分享创造：桌面自动化的 post 断言和 undo，我做成了协议`

### 正文

> 先说没做到的，省得看完再失望：
>
> - **Linux 没驱动**，只能用文件类 skill，UI 场景要等 AT-SPI2；
> - **录制器是 300ms 轮询**，快速切换窗口会漏，而且只抓左键；
> - **公共 npm 没发**，现在只有 install.ps1、GitHub Packages、clone 三条路。
>
> 然后是它到底在做什么。
>
> 我写过的每段桌面自动化都有同一个毛病：第五步悄悄失败了，前四步已经改了机器，没有人知道该退到哪。所以我把"怎么算成功"和"怎么退回去"变成协议里的硬约束，而不是文档里的建议：
>
> - skill 只产出动作（`plan() → Action[]`），不准碰系统 API；
> - 每个动作必须带一条 post 断言和一条 undo，不可撤销的动作会被协议直接拒收；
> - 默认是预览，不加 `--mode apply` 一步都不执行；
> - 断言失败：先撤掉失败动作自己的副作用，再把前面成功的步骤逆序回滚，然后写日志；
> - 所有步骤（包括失败的）都进 JSONL 审计日志，带 taskId、actionId、状态和撤销方式；
> - 内核里没有任何模型，模型只能待在 skill 的 `see()` / `plan()` 后面，所以断网可用、不需要 key。
>
> 协议 v0 已经冻结在 `spec/protocol-v0.json`：8 种 action、7 种断言类型、5 种 undo、7 个 capability。冻结之后只能加向后兼容的字段，改语义要走 RFC。
>
> 三十秒验证（Node >= 22.18，零第三方依赖，不用 npm install）：
>
> ```
> git clone {仓库地址} && cd deskshell
> node bin/deskshell.ts doctor
> node scripts/make-fixture.ts
> node bin/deskshell.ts run downloads-cleanup --root .demo/downloads              # 只预览
> node bin/deskshell.ts run downloads-cleanup --root .demo/downloads --mode apply
> node bin/deskshell.ts run downloads-cleanup --root .demo/downloads --mode undo
> node bin/deskshell.ts story --fail                                              # 看它失败后自己撤
> ```
>
> 现在最缺的三样，按我认为的价值排：Linux AT-SPI2 驱动 > 多显示器/DPI 的坐标映射 > 录制器改成事件钩子（现在是轮询）。驱动接口只有六个必选方法，写起来不离谱。
>
> 想听的是反对意见：**把信任边界放在"每个动作的 post 断言"上，是不是放错了地方**？还是应该放在任务级？我现在只有自己的判断。
>
> 不想回帖也行：跑一次 `node bin/deskshell.ts story --fail`，三十秒，看完再决定要不要说话。

## 4. 掘金 / 知乎

### 掘金 · 三个选题（按优先级）

1. **"为什么每个桌面动作都必须写 post 断言"** —— 讲"调用返回成功"和"事情真的发生了"之间的差距，配真实失败例子。
2. **"失败回滚的顺序：先自撤还是先逆序"** —— 讲 0.1.0 和 0.3.0 修过的两次回滚 bug（留孤儿文件；前置断言失败时不该自撤）。
3. **"给桌面操作加 undo 和审计，我踩的四个坑"** —— 网络副作用不可撤销、窗口几何逐像素还原、目录层级撤销不干净、录制器漏采。

> 不要写"XXX 从入门到精通"，不要把 README 翻译一遍。读者要的是别人的坑，不是项目的介绍。

### 文章开头（以选题 1 为例，可直接用）

> 一段桌面自动化脚本里有这么一行：`click(button)`。它返回了，没抛异常，于是脚本继续往下走。三分钟后你发现那个按钮根本没被点到——它被一个后来弹出的提示框挡住了，或者元素句柄已经过期，调用照样"成功"。
>
> 这类 bug 最难查的地方在于：**每一次调用都告诉你它成功了**，只有最终结果不对。所以我把"怎么算成功"从注释里搬到代码里：每个动作必须声明一条 post 断言，断言不成立就停，并且回滚。
>
> 这篇讲三件事：断言该写在哪一层、写多强算够、以及在真实项目里它救过哪些场。

### 文章结构（四段，每段一个可验证的东西）

1. **问题**：一次 silent failure 的完整过程（命令 + 输出，不要编，用自己跑出来的）。
2. **为什么"重试"和"多等两秒"治不好**：延迟是表象，缺少可观测的效果才是原因。
3. **做法**：post 断言写在动作里；断言要观察"效果"而不是"调用"；失败后的回滚顺序（先自撤，再逆序）。
4. **代价**：写断言的时间比写动作长；有些动作根本没法写断言（网络副作用），这类动作在协议里会被直接拒收——这是设计，不是缺陷。

文末一段放仓库链接和一个 30 分钟动作：`node bin/deskshell.ts story --fail`，看一次真实的失败回滚。

### 知乎 · 回答优先

找已经有流量的老问题答，不要自己开新问题。适合的两类：

- "AI 操作电脑 / computer use 现在靠谱吗" → 答"靠谱不靠谱取决于有没有断言和回滚"，讲机制不讲愿景。
- "RPA / UI 自动化怎么保证稳定性" → 答三个具体手段：效果断言、句柄失效后的几何重解析、失败即回滚而不是继续。

开头（可直接用）：

> 结论先说：现在这类东西的稳定性瓶颈不在模型，在**没有人在事后能说清发生了什么**。我按这个思路做了半年多，聊一下具体怎么做，以及哪些地方根本做不到。
>
> 文末固定放一个 30 分钟动作：`node bin/deskshell.ts doctor`，一条命令告诉你这台机器支持到什么程度；想看不带模型的失败回滚，`node bin/deskshell.ts story --fail`。
