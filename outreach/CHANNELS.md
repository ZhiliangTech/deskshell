# 渠道作战手册 · deskshell 冷启动

> 这份文件管的不是曝光，是**把陌生人推进到 30 分钟实验**。
> 唯一成功标准：一个此前不认识这个项目的人，在你的触达之后跑完了 `node bin/deskshell.ts doctor`，并且看到了一次 undo。
> 周期：30 天。30 天后按第 8 节判定重写，不自动续期。

---

## 0. 口径统一：只准说这些，并且能指出出处

外联文案里每个技术名词都会被人拿去验。下面这张表是全部弹药，出处都是仓库里的文件；表外的话不要说。

### 不可以说

- 任何 star 数、fork 数、用户数、下载量、留存率。**除非**是自嘲式的、且当场可查（默认不做）。
- "生产可用"、"企业级"、"已有 X 家公司采用"。
- 性能倍数、与同类项目的 benchmark 对比（我们没跑过对方的测试）。
- "竞品做不到"。只能说我们自己做了什么。
- 颠覆、革命、重新定义、宇宙第一、唯一、最强、斩获。
- 未发生的路线图当承诺讲（"下个月支持 Linux"）。没合并的 PR 不存在。

### 一句话定位（反复用同一句，别换花样）

> **把电脑塞进 agent 里：每个动作可声明、可断言、可撤销、可审计；内核里没有模型。**

English: **The machine as a toolbox inside the agent: every action is declared, asserted, undoable, audited — no model in the kernel.**

## 1. 渠道卡

转化按两个数看：**触达 → 回复**，**回复 → 跑过 doctor**。下面的预期转化是**估算值（未实测，用来排优先级，不是承诺）**，第一次复盘时用真实数据替换。

### 1.1 GitHub：相关仓库的 issue / discussion 技术评论

- **适合谁**：写过 UI 自动化、桌面 RPA、accessibility 工具的人。他们已经在同一个坑里。
- **发什么**：先解决对方的问题——复现步骤、日志分析、一个能用的 workaround、一段可粘贴的代码。项目名只出现在最后一段，而且只在真的相关时。模板见 `messages/en.md` 第 4 节。
- **禁忌**：不要在别人的 issue 里贴"我做了个类似的东西，来看看"；不要一次触达多个仓库（同一周内不超过 2 个仓库，且必须真的在用它）；不要留任何 star 请求；不要复制粘贴同一段评论（GitHub 会显示你的评论历史）。
- **预期转化**：估算 触达 10 条 → 1–2 条有价值回复 → 0–1 人跑命令。这是所有渠道里**留存最高**的，因为对方已经在这类问题上投入过时间。
- **每天配额**：**2 条**。每条至少读 3 个相关 issue 再写。写不出真东西就当天记 0。

### 1.2 GitHub：awesome-list PR

- **适合谁**：维护 awesome-* 列表的人（自动化、computer-use、accessibility、reverse-engineering 工具类）。
- **发什么**：一次只提一个列表。描述按列表模板写一行，不多加形容词；在 PR 描述里写清"解决了列表里哪一类空白"。
- **禁忌**：不要一次批量提 10 个列表（会被判为 spam，且以后进不去）；不要改别人的行；不要在 PR 里写长推销文案。
- **预期转化**：估算 提交 5 个 → 2–3 个合并 → 带来的访问量很小，但**外链权重和"被发现"的概率**是长期的。
- **每天配额**：**每周 3 个**（不是每天）。提交前先看该列表最近 20 个 PR 的合并标准。

### 1.3 GitHub：topic 标签与仓库门面

- **适合谁**：在 GitHub 上搜 `computer-use`、`uia`、`desktop-automation` 的人。
- **发什么**：仓库 topics 收敛到 6–8 个真实相关的词（`computer-use`、`desktop-automation`、`accessibility`、`rpa`、`undo`、`audit`）；README 首屏第一句必须能在 5 秒内说清"和普通脚本的区别"（现在的表格已经做到）。
- **禁忌**：不要堆 20 个 topic；不要把 `ai`、`llm` 放在第一位（内核里没有模型，放第一位会引来错误预期，然后在评论区被打）。
- **预期转化**：不直接转化，但它是**所有渠道的落地页**。别的渠道把人送到这里，这里说不清就全废。
- **每天配额**：一次性设置，之后每周看一次。

### 1.4 Hacker News（Show HN）

- **适合谁**：HN 上的系统/工具类读者。他们对"事务语义"这种词有反应，对"AI agent"疲劳。
- **发什么**：标题必须以 `Show HN:` 开头，5 个备选见 `messages/en.md` 第 5 节。正文说清：这是什么、怎么跑、已知限制（把 Linux 只有窗口层、录制器还没抓拖拽/右键菜单/滚轮、npm 未发布写进去——HN 最恨隐瞒限制）。
- **时机**：周三或周四，美东时间 8:00–10:00 之间提交（估算的最佳窗口，未实测）。提交后 3 小时内必须守在评论区逐条回。
- **禁忌**：不要找人 upvote（会被识别并降权）；不要用营销句式；不要在正文里放"请给 star"；不要在评论里和质疑者辩论——只补事实和数据。
- **预期转化**：估算 100–300 次访问 → 5–15 人真跑 → 1–3 条 issue。**一次 Show HN 的绝对量最大，但留存不如 1.1。**
- **每天配额**：**30 天内最多 2 次**（第二次必须是因为第一次之后有实质变化，例如 Linux 控件层落地）。

### 1.5 Reddit（r/LocalLLaMA、r/opensource、r/automation、r/computeruse）

- **适合谁**：`r/computeruse` 与 `r/LocalLLaMA` 的人真的在跑本地模型 + 桌面操作；`r/opensource` 更看维护质量；`r/automation` 偏业务自动化，对"事务/回滚"接受度高。
- **发什么**：帖子要先给一个可复现的过程（命令 + 输出），再说项目。每个版的标题和角度不同，不要一稿多投。
- **禁忌**：各版规则以**当前 sidebar 与置顶帖为准**（karma 门槛、账号年龄、自我推广比例通常在 9:1 左右）；不要首帖就是链接帖；不要跨版复制同一段正文（有人会查你的发帖历史）；r/opensource 对纯推广尤其严。
- **预期转化**：估算 单个版 30–80 次访问 → 2–5 人跑 → 0–1 条 issue。发 4 个版分散在一周内，不要同一天。
- **每天配额**：**每周 2 个版**。发之前先在版里认真回 3 个别人的帖（不是灌水，是真回）。

### 1.6 X / Twitter

- **适合谁**：跟着 AI agent / computer-use 话题的开发者与工具作者。
- **发什么**：5 条 thread（`messages/en.md` 第 7 节），核心是**一条能看懂的差异**：失败时先自撤再逆序回滚，输出贴真实命令结果。配一张终端截图（不要做花哨图）。
- **禁忌**：不要 @ 大 V 求转发；不要用"🚀"堆砌；不要在一条推里塞 5 个链接；不要日更 5 条（会被当 bot）。
- **预期转化**：估算 单条 thread 200–1000 曝光 → 1–5 次点击 → 0–1 人跑。**这是曝光渠道，不是转化渠道**，别在这里算 KPI。
- **每天配额**：**1 条**（含回复别人的技术讨论）。每周至少 3 条是纯技术、不含项目链接。

### 1.7 V2EX（分享创造节点）

- **适合谁**：中文独立开发者、工具作者。对"做了一半就发出来"很宽容，对营销腔极其敏感。
- **发什么**：`messages/zh.md` 第 3 节。开头必须自曝限制（Linux 只有窗口层、录制器还没抓拖拽和右键菜单、npm 还没发），然后给三条命令。
- **禁忌**：不要在多个节点重复发；不要标题带"重磅/开源神器"；不要在正文里求 star；不要用"我们"（就一个人写的东西，说"我"）。
- **预期转化**：估算 300–800 阅读 → 5–15 条回复 → 3–8 人跑 → 0–2 条 issue。中文渠道里**唯一稳定出真实反馈**的地方。
- **每天配额**：**30 天内 2 帖**（首发 + 有实质更新后的一帖）。发帖当天要守着回帖。

### 1.8 掘金

- **适合谁**：中文前端/Node 开发者。搜索流量长尾。
- **发什么**：技术文，不是项目文。选题优先级：①"我用 300 行实现了一个可撤销的桌面操作内核" ②"为什么每个动作都要有 post 断言" ③"失败回滚：先自撤还是先逆序"。文末一段放仓库链接。
- **禁忌**：不要写"XXX 从入门到精通"；不要把 README 翻译一遍当文章；不要开篇讲愿景。
- **预期转化**：估算 单篇 200–1000 阅读 → 1–3 人点仓库 → 0–1 人跑。**长尾**：三个月后还在带访问。
- **每天配额**：**每周 1 篇**，30 天 4 篇。宁可 2 篇写透，不要 4 篇水。

### 1.9 知乎

- **适合谁**：搜"AI 操作电脑"、"RPA 怎么做"、"自动化测试 稳定性"的人。
- **发什么**：回答优先于发文章。找 3–5 个已有流量的老问题，写**具体做法**（断言怎么写、回滚顺序为什么重要），末尾一句"代码在这里"。
- **禁忌**：不要写"如何看待 XXX"式空谈；不要贴长图代替文字；不要一个回答里放三个项目链接。
- **预期转化**：估算 单回答 500–3000 阅读 → 2–6 人点仓库 → 1–2 人跑。转化率低于掘金，但**单条寿命更长**。
- **每天配额**：**每周 1 个回答**。

### 1.10 小红书

- **适合谁**：非开发者居多，但有一批"效率工具"受众。**这个渠道的真实价值不是拉贡献者，是练表达**——被非技术听众听懂，说明定位真的清楚。
- **发什么**：30 秒口播（`messages/zh.md` 第 5 节）。画面就是终端：跑 preview、跑 story --fail、看它回滚。
- **禁忌**：不要用"打工人必备"、"效率神器"；不要加滤镜和 BGM 盖住键盘声；不要在标题写"AI"三次。
- **预期转化**：估算 500–3000 播放 → 5–20 次主页访问 → 0–1 人真跑。**不要把它算进贡献者 KPI。**
- **每天配额**：**每周 2 条**，30 天 8 条。用同一条口播稿换开头重录，不要一次录 8 条不同的。

### 1.11 Discord / Slack（AI agent、RPA、accessibility 社区）

- **适合谁**：在 `#showcase` / `#projects` / `#help` 里活跃的人。
- **发什么**：先在其他频道回答 5 个问题（真的答，带命令和文档链接），再在 showcase 发一次自我介绍（`messages/en.md` 第 8 节）。之后只在该社区有人问"桌面点击老是不稳"时出现。
- **禁忌**：不要一进群就发链接（多数服务器有反 spam bot，直接踢）；不要 DM 陌生人（这条是硬线）；不要跨服务器复制同一段话。
- **预期转化**：估算 一个服务器 1–3 人跑。**慢，但来的人是复访的**——Discord 里出现过的名字，后面 PR 概率最高。
- **每天配额**：**每天 15 分钟**泡 2 个服务器，回答 1 个问题。发项目链接每周不超过 1 次/服务器。

### 1.12 播客 / newsletter 投稿

- **适合谁**：做开发者工具、开源、AI agent 主题的中小播客与周报（几百到几万订阅）。
- **发什么**：一封 150 词的 pitch（`messages/en.md` 第 3 节的邮件版可复用），只讲一个可讲的故事："AI 点了鼠标，怎么证明它点对了，错了怎么退回去"。附 3 条可复现命令。
- **禁忌**：不要群发（BCC 一次 50 个 = 全部拉黑）；不要附 zip；不要在第一次邮件里要"专访"。
- **预期转化**：估算 发 10 封 → 1–2 封回复 → 0–1 次露出。**期望值低，但一次露出的寿命是 6 个月**（播客会被长期搜到）。
- **每天配额**：**每周 3 封**，30 天 12 封上限。同一家不发第二封（除非对方回了）。

### 1.13 线下 meetup

- **适合谁**：本地 Node / Python / 自动化 / accessibility 聚会。
- **发什么**：不去讲项目，去讲**一个问题**（"AI 点了鼠标，你怎么知道点对了"），现场演示 90 秒：preview → apply → 故意失败 → 回滚。带笔记本，能现场跑。
- **禁忌**：不要发传单；不要占用 Q&A 时间推销；不要在别人的 lightning talk 后抢话。
- **预期转化**：估算 一场 30 人 → 3–5 人当场加联系方式 → 1–2 人一周内跑。**单位时间转化率最高的渠道**，但一个月能有一场就不错。
- **每天配额**：**每周报名 1 场**，30 天内至少出席 1 场（哪怕只是听众，Q&A 提一个问题）。

## 3. 每日例行（45 分钟，不要超）

1. **10 分钟**：GitHub 通知 + 相关仓库新 issue（只看 3 个仓库）。
2. **15 分钟**：2 条技术评论（1.1），或 1 条 Discord 回答（1.11）。
3. **10 分钟**：回复所有私信与评论。**当天回，不要攒。**
4. **10 分钟**：更新名单表与 KPI 表（第 7 节的字段），当天没触达就写 0。

写不出有价值的东西的那天，就只做第 3 步。**空转一天比发一条垃圾触达好。**

---

## 4. 跟进规则

- **每人最多 2 次跟进**：首次触达 → 跟进 1 → 跟进 2，之后**永久停止**。
- **间隔 5–7 天**。少于 5 天是骚扰，多于 10 天对方已经忘了你。
- **跟进 1 必须带新东西**：一条具体 issue 链接、一个他提过的场景的复现、一段改好的代码。没有新东西就不发。
- **跟进 2 是最后一次，必须给出口**：明确写"这是最后一封，之后不再打扰"，并给一个不需要回应的选项（例如"如果你只是想要更新，watch repo 就够"）。
- **不群发**：一封邮件一个收件人，BCC 一律不用。被发现群发的代价是这个人以后再也不会读你。
- **不跨渠道追人**：在 X 上没回，不要再去他 GitHub issue 里出现。同一个人在同一周内只在一个渠道被触达一次。
- **被拒绝就停**：任何形式的"不用了/没兴趣/现在不行"，一律回一条婉拒回复（`messages/en.md` 第 11 节 / `messages/zh.md` 第 7 节），然后从名单里划掉，30 天内不再出现。

## 6. 每条触达都必须带一个 30 分钟动作

这是整套文案唯一的硬约束：**任何一条触达，结尾必须给一个 30 分钟内能做完、且不需要读懂整个项目的动作。**只有三个选项，不要发明第四个：

1. **跑 doctor**：`git clone` → `node bin/deskshell.ts doctor` → 看 7 项检查结果。
2. **写一个 skill**：`node scripts/new-skill.ts --name my-skill` → 只改 `plan()` → `--mode preview`。
3. **认领一个 issue**：roadmap 里"不需要决策"的条目对应的 issue（Linux AT-SPI2 驱动、多显示器/DPI 坐标映射、录制器补拖拽/右键菜单/滚轮、`window.rect` 断言推断、dry-run diff、撤销时间线、`run --parallel`、故障注入、文档站搜索）。

动作必须**可判定完成**："看看仓库"不算动作。

## 7. 记录表与 KPI

### 名单 / 触达表字段（一行一个人）

```
name | handle | channel | why_them(一句话，必须具体到他的某个项目/issue) | first_contact_date |
variant(A/B/…) | replied(y/n/日期) | ran_doctor(y/n/日期) | issue_or_pr(链接) |
followup1_date | followup2_date | status(active/declined/dead) | note
```

`why_them` 写不出来的人，不要发。

### KPI（30 天结算，不要美化）

| 指标 | 定义 | 30 天目标（**设定值，不是实测**） | 低于这个数说明什么 |
| --- | --- | --- | --- |
| 发出数 | 真实一对一触达（私信/邮件/技术评论），不含公开帖 | 60 | 执行力问题，不是渠道问题 |
| 回复率 | 有实质回复 / 发出数 | ≥ 15% | 低于 10% = 文案或选人有问题，先改 `why_them` |
| doctor 落地数 | 明确说跑过 `doctor` 的人 | ≥ 8 | 低于 5 = 文案结尾的动作不够具体 |
| 首个外部 PR | 非本人提交、被合并的 PR | ≥ 1 | 0 = 第 3 周的 issue 没标清验收标准 |
| 贡献者留存 | 首个 PR 之后 14 天内还有第二次互动（评论/issue/PR）的人 | ≥ 50% | 低 = 评审太慢或态度冷 |
| 公开内容产出 | 发出去的技术文/帖子 | 掘金 4、V2EX 1–2、Reddit 2、X 15 条、HN 1 | 少 = 第 2 周没执行 |

**不统计**：曝光量、点赞、star。它们和"有人跑过命令"没有稳定关系，统计它们只会让人自我安慰。

## 8. 怎么判断一个渠道死了

满足任意两条，判定为死，**停 2 周，只在有实质产品变化后重启一次**；再死就永久放弃这个渠道，把时间给活着的渠道。

1. **连续 10 次触达 0 实质回复**（"谢谢"不算回复）。
2. **连续 3 次发帖 0 评论、0 仓库点击**（用仓库 Insights 的 referrer 判断，不用感觉）。
3. **名单枯竭**：该渠道上你能写出 `why_them` 的人少于 5 个，且已全部触达过。
4. **规则封死**：版规/服务器规则明确禁止自我推广，或你的账号已被限流（发帖不进新版块首页）。
5. **来的都是错的人**：回复集中在"能不能自动抢票/自动刷单/自动过验证码"——说明这个渠道的受众和项目定位不匹配，继续投入只会拉低讨论质量。

**渠道死掉不等于项目有问题**，通常只是这个池子里没有你的前 10 个用户。换池子，不要改定位。

### 各渠道的早期死亡信号（一句话）

| 渠道 | 最早的死相 |
| --- | --- |
| GitHub issue 评论 | 你的评论被 maintainer 回"这与本 issue 无关" —— 说明价值没给够，不是渠道问题 |
| Show HN | 2 小时内没有一条评论、排名掉出前 60 —— 标题没打出差异，换标题再等 30 天 |
| Reddit | 帖子被 automod 秒删 —— 账号资格不够，先养 2 周再发 |
| X | 每条 thread 曝光 < 100 —— 账号没有技术受众，改用回复别人而不是发原创 |
| V2EX | 发帖 24 小时 0 回复 —— 标题没有具体问题，改标题 |
| 掘金 | 阅读 < 100 —— 选题是"介绍项目"而不是"解决一个具体问题" |
| 知乎 | 回答被折叠或 0 赞 —— 你在答一个没人搜的问题，换问题不换内容 |
| 小红书 | 完播率无法查看但收藏为 0 —— 受众拿不到可执行的动作，把"跑命令"画面提前到第 3 秒 |
| Discord/Slack | 发言被忽略超过 5 次 —— 你在 showcase 里发得太多、在 help 里答得太少 |
| 播客/newsletter | 12 封 0 回复 —— pitch 太长，砍到 100 词，只留一句差异 |

## 9. 30 天后要回答的三个问题

1. 哪 3 个人真的跑过命令？他们是从哪个渠道来的？
2. 第一个外部 PR 是谁提的？他在提之前和你互动过几次？
3. 如果只剩一个渠道能继续，是哪个？为什么不是另外两个？

答不出来 = 这 30 天的记录表没认真填，重做第 7 节而不是加渠道。
