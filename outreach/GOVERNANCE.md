# 治理

这份文件说明：**谁在什么范围内说了算，改动怎么被批准，吵起来怎么办。**

先说实话，免得读到后面才发现前提不成立：项目目前只有一位维护者（`@ciceroyang`），外部贡献者为零。所以下面写的分工，是**现在就开始执行、而不是等有人了再补**的规则——它的作用是让第一位贡献者进来时，边界已经是清楚的，而不是每次都由人临时拍脑袋。

## 1. 决策权的划分

按改动**影响谁**来分，不按改动大小分。

| 范围 | 谁说了算 | 怎么批 | 依据 |
| --- | --- | --- | --- |
| 内核协议（`spec/protocol-v0.json`、`packages/core/src/types.ts` 的 action / assertion / undo 语义、`kernel.ts` 的事务与回滚语义） | 维护者 + RFC | 必须有一份被接受的 RFC，且回归证据完整 | 本文件第 2 节 |
| 驱动的接口实现（`packages/drivers/<platform>/`） | 该平台的 Driver Maintainer | 单个 PR + `scripts/verify-driver.ts` 在该平台通过 | [CONTRIBUTOR-LADDER.md](CONTRIBUTOR-LADDER.md) L3 |
| 驱动接口本身（`UiDriver` 的方法签名） | 维护者 + RFC | 加方法可以走 PR（增量），改已有方法语义必须走 RFC | 见第 2 节的"什么算破坏性" |
| Skill（`packages/skills/<name>/`） | 作者自治，但受 manifest 约束 | 作者自己决定实现，只要通过内核校验与 CI | 见第 1.1 节 |
| 文档、站点、示例 | 任何贡献者 | 一个 PR，一位 reviewer 通过 | — |
| 发布、版本号、发布渠道 | 维护者 | — | — |

### 1.1 Skill 作者自治的边界

作者对 `plan()` 里怎么写有完全的自由。但下面四件事不是作者的自治范围，而是内核的硬约束，PR 里被拒绝时不需要讨论：

1. 每个动作必须有 `post` 断言；断言必须机器可判（文件存在、控件值、数量），不能是"看起来没问题"。
2. 每个动作必须有 `undo`。确实不可撤销的，必须显式写 `undo: null` 并承担被内核拒绝的后果——这是设计，不是 bug。
3. 能力必须声明、必须有 `reason`、scope 不能宽于实际需要。内核按声明校验，未覆盖的动作会被拒绝。
4. `plan()` 里不许直接调系统 API，也不许调模型。模型只能出现在 skill 的 `see()` / `plan()` 之后的可替换接口里。

除此之外还有一条**不由内核强制、但由评审强制**的：一个 skill 不能靠"只在某台机器上能跑"来合并。它必须在 `scripts/regress.ts` 里有检查（见 [GOOD-FIRST-ISSUES.zh-CN.md](GOOD-FIRST-ISSUES.zh-CN.md) 各任务的验收标准）。

### 1.2 激励结构：没有现金，说清楚

项目**不设现金悬赏**（2026-10-30 定稿）。`bounty` 标签的含义是"可认领、有验收标准、有 mentor"，不涉及任何报酬；issue 模板、两版任务板、README 都写明了这一点，避免有人冲着钱来认领。

贡献者实际拿到的是：

1. **所有权**——驱动由平台维护者长期持有；skill 由作者自治。
2. **署名**——`CONTRIBUTORS.md` 按真实贡献类型分节，release notes 写明谁做的。
3. **优先评审**——首次响应 48h，小 PR 72h 内给结论。
4. **路线图投票权**——2 个合并 PR 之后生效（见 1.3）。

### 1.3 路线图投票（已公开）

- 任何有 **2 个已合并 PR** 的贡献者，对路线图上"需要拍板"的条目拥有**正式一票**。
- 投票在 GitHub Discussions 的 Polls 分类里公开进行（当前一轮：<https://github.com/ZhiliangTech/deskshell/discussions/11>），不搞私下征询。
- 计票规则：一人一票，投票期 14 天；平票时给"第一个 PR 最小"的选项。
- 维护者保留**否决权**，但必须公开写理由（通常是破坏协议不变量或零依赖约束）。

## 2. RFC 流程

完整模板与状态机在 [rfcs/README.md](../rfcs/README.md)。这里只说治理层面的规则。

### 2.1 什么必须走 RFC

- 改 `spec/protocol-v0.json` 的任何内容。
- 改 `Action` / `Assertion` / `Undo` 的已有语义（新增类型属于协议变更，也走 RFC；给驱动加方法是例外，见下）。
- 改内核的事务边界：什么时候回滚、回滚到什么程度、失败如何进日志。
- 新增第三方运行时依赖（这会破坏零依赖不变量）。
- 改许可、改贡献者政策、改本文件。

### 2.2 什么不需要 RFC

- 给 `UiDriver` **增加**方法（现有实现退回 `not implemented` 即可，`scripts/verify-driver.ts` 会把未实现项标成 `SKIP`）。
- 新增 skill、修 bug、改文档、改测试、加 CLI 只读命令。
- 内部格式变更，例如录制器 JSONL 的结构——它不属于协议 v0，但改了要更新 `docs/recording.md`。

判断标准很简单：**这个东西一旦发出去，别人的代码会不会因此必须改？** 会，就是 RFC。

### 2.3 RFC 从提出到落地的路径

1. 开 issue 说"我要写 RFC"，一句话讲清动机。维护者 7 天内回应。
2. 按模板写 `rfcs/NNNN-slug.md`，状态 `Draft`，开 PR。
3. 状态转 `Review` 后进入评审窗口，至少 **7 天**，任何人可以提反对意见。
4. 接受需要维护者 approve；被拒必须写理由，理由进 RFC 文件本身，不只在 PR 评论里。
5. 合并后状态 `Accepted`。**实现是另一个 PR**，实现落地后状态转 `Implemented`，并同时更新 `CHANGELOG.md` 的迁移说明。

一个 RFC 被接受但两周内没人实现，维护者可以把它降级回 `Draft`——避免"看着已经决定了"的假象。

## 3. 冲突处理

### 3.1 技术分歧

默认走**惰性共识**：提出方案的人给出理由与证据，7 天内无人提出有理由的反对，就按方案执行。

出现反对时：

1. 反对者必须写清**具体后果**（哪条不变量被破坏、哪个既有 skill 会坏、哪条测试会红），"我不喜欢"不算理由。
2. 双方各自给出可验证的判据。能在十分钟内跑一条命令分出对错的，就去跑，不辩论。
3. 仍然分歧时，由该范围的决策者裁决（见第 1 节的表），**必须书面写裁决理由**，并且写进对应的 issue 或 RFC 文件。

### 3.2 决策者自己违反规则时

维护者绕过 RFC 合并了协议改动，任何人都可以开 issue 标题写 `[meta] governance breach`，并把 PR 链接贴进去。处理方式：维护者在 7 天内要么补 RFC，要么回滚。这条是给自己上锁，不是给别人看的。

### 3.3 人际冲突

技术上的直接是可以的，对人的攻击不行。人身攻击、歧视、骚扰——一次即移除，见 [CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md)。技术分歧不触发移除，也永远不会被当作"态度问题"处理。

## 4. 提交者晋升

阶梯的完整定义在 [CONTRIBUTOR-LADDER.md](CONTRIBUTOR-LADDER.md)，这里只说治理相关的那部分：

- **L3 Driver Maintainer**：由维护者指派，条件是该平台驱动有被合并的实现 + `scripts/verify-driver.ts` 通过 + 至少一次对他人改动的实质评审。指派后该平台 PR 需要其 approve 才能合并；同时新建 `.github/CODEOWNERS` 把该目录指给他（这个文件目前还没有，指派时一并建）。
- **L4 Protocol Reviewer**：条件是一份被接受的 RFC 或三次改变结论的 RFC 评审。达成后，改协议或内核语义的 PR 必须有其 approve。
- **L5 Maintainer**：由现有维护者一致提名，条件见阶梯文件。获得写权限、合并权、发布权、否决权。

晋升决定必须写在公开 issue 里，不通过私信完成。降级同理：如果一位 L3/L4 连续 90 天无法响应（且没有提前说明），权限转入"候补"状态，直到其回来或明确退出——这不是惩罚，是为了让其它贡献者不被卡住。

## 5. 与行为准则的衔接

- 所有治理流程（issue、PR、RFC 评审、冲突裁决）都在 [CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md) 的约束下运行。
- 行为准则的执行者是维护者；涉及维护者本人的投诉，走 `[meta]` issue 公开提出，接受公开审视。
- 因行为准则被移除的人，其技术贡献不会被删除（历史提交、已合并代码保留），但不再出现在 `CONTRIBUTORS.md` 的活跃贡献者表中。

## 6. 现在能做的三件事

1. 想改协议：先看 [rfcs/README.md](../rfcs/README.md) 的模板，开 issue 说动机。
2. 想接管一个平台：看 [GOOD-FIRST-ISSUES.zh-CN.md](GOOD-FIRST-ISSUES.zh-CN.md) 的任务 01、02，那是通往 L3 的路。
3. 对治理本身有意见：开 issue，标题前缀 `[meta]`。这份文件不是石刻。
