# 贡献者阶梯

这份文件回答一个问题：**我在这里能走到哪，走到那一步要交什么，交完能得到什么。**

项目现在很年轻——仓库公开、一个维护者、外部贡献者还是零。阶梯不是许愿池，是从第一天就能兑现的承诺：下面每一级的"达到条件"都能被一次 PR 或一次评审记录验证，"获得什么"里没有一条需要等融资、等公司、等排期。

五级：

| 级别 | 名字 | 一句话 |
| --- | --- | --- |
| L1 | 第一次 PR | 你交了一个可合并的改动 |
| L2 | Skill Author | 你写的 skill 有人在用，且你能自己维护它 |
| L3 | Driver Maintainer | 某个平台的驱动归你管 |
| L4 | Protocol Reviewer | 协议变更必须经过你的评审 |
| L5 | Maintainer | 你有合并权与否决权 |

---

## L1 — 第一次 PR

**达到条件（任一）**

- 一个 PR 被合并，且它至少满足：改了代码或文档、CI 绿、验收命令的输出贴在 PR 里。
- 具体例子：修一个错别字也算，但必须是真错——维护者不会为了凑数合并；[GOOD-FIRST-ISSUES.zh-CN.md](GOOD-FIRST-ISSUES.zh-CN.md) 里的 S 级任务是最短的路径。

**获得什么**

- 名字进 `CONTRIBUTORS.md`（PR 里自己加一行即可，见该文件的"怎么把自己加进来"）。
- 进 issue 时可以要求维护者优先看你的下一个 PR（在 issue 里直接写"L1，想接着做 X"）。
- 首次响应 **48 小时**内的承诺对你生效（见下面的评审 SLA）。

**下一步怎么走**

挑第二个任务时优先选**同一领域**的，一般在 S/M 级；连续两个 PR 都在同一领域且都被合并，就够 L2 的门槛了。

---

## L2 — Skill Author

**达到条件（全部满足）**

1. 至少一个 skill 被合并进 `packages/skills/`，并且它遵守三条硬规则：每个动作有 `post` 断言、每个动作有 `undo`、`plan()` 里不直接调系统 API（[CONTRIBUTING.md](../CONTRIBUTING.md)）。
2. 这个 skill 在 `scripts/regress.ts` 里有一条自己的检查，也就是说它在 CI 上是**被测过的**，不是只在你的机器上跑过一次。
3. 至少一次：别人（维护者或其它贡献者）提的 issue 或 PR 指出了你的 skill 的问题，你在 7 天内处理完。

**获得什么**

- `CONTRIBUTORS.md` 的 *Skill* 一节有你的条目，链接到你写的 skill。
- 你写的 skill 出问题时，维护者先 @ 你，而不是直接改你的代码——除非你 14 天没回应。
- roadmap 讨论里，你对自己 skill 范围内的方向有优先发言权。
- 可以要求成为某个 skill 目录的 CODEOWNER（在 issue 里说一声，维护者加进 `.github/CODEOWNERS`）。

**下一步怎么走**

L3 不是"写更多 skill"，而是"接管一个平台"。如果你更想深耕 skill，可以停在 L2 并横向扩张——这完全正当，阶梯不是必须往上爬的楼梯。

---

## L3 — Driver Maintainer

**达到条件（全部满足）**

1. 你实现了某个平台的驱动，或对它做出了被合并的实质性改动（新增能力、修坐标、修控件树遍历），并且 `scripts/verify-driver.ts` 在该平台上能跑出 `PASS`。
2. `docs/drivers.md` 里那个平台的"已验证 / 未验证 / 已知限制"三栏由你维护，且内容与代码一致。
3. 你至少评审过别人对该平台的一次改动，并给出了具体意见（不是"LGTM"）。

**获得什么**

- `CONTRIBUTORS.md` 的 *Driver* 一节有你的条目。
- 该平台的 issue 默认指派给你；别人对该平台的 PR 需要你的 review 才能合并。
- 你对该平台的路线图有决定权：要不要支持某个控件类型、要不要放弃某个旧系统版本，你说了算（协议层面的仍然要走 RFC）。
- 维护者可以给你 GitHub team 邀请（例如 `drivers` team，用于指派与通知）。

**下一步怎么走**

L4 的入口是评审，不是写代码。开始主动看 `packages/core/src/` 的 PR，在 issue 里写下你的判断和理由；被采纳三次以上，维护者会主动问你。

---

## L4 — Protocol Reviewer

**达到条件（全部满足）**

1. 你写过至少一份被接受的 RFC（[rfcs/README.md](../rfcs/README.md)），或者对三份以上 RFC 给出过改变结论的评审意见。
2. 你能说清楚协议 v0 的四个不变量：动作必须有 `post`、动作必须有 `undo`（`undo: null` 会被拒绝）、能力必须声明且被校验、内核零模型依赖。能在评审里指出一个 PR 违反了哪一条。
3. 你至少发现过一次"现有 skill 的预览快照会变"的破坏性改动——`scripts/snapshot-test.ts` 与 `scripts/protocol-freeze-test.ts` 是用来抓这个的，你得知道它们各自在守什么。

**获得什么**

- `CONTRIBUTORS.md` 的 *Protocol* 一节有你的条目。
- 任何改 `spec/protocol-v0.json`、`packages/core/src/types.ts` 或内核语义的 PR，**合并前必须有你的 approve**。
- RFC 状态从 `Draft` 走向 `Review` 时，你是默认评审人之一。
- roadmap 投票：需要拍板的条目（见 [docs/roadmap.md](../docs/roadmap.md) 末尾那五件事）你有正式一票。

**下一步怎么走**

L5 由现有维护者提名。判断标准不是技术水平，而是"这个人是否愿意在没人看的时候也把边界守住"——包括拒绝一个自己很喜欢但会破坏不变量的 PR。

---

## L5 — Maintainer

**达到条件（全部满足）**

1. 在 L4 上稳定工作至少三个月，期间没有因为"差不多就行"而放过破坏性改动。
2. 处理过至少一次冲突（见 [GOVERNANCE.md](GOVERNANCE.md) 的冲突处理），并把结论写进了公开记录。
3. 现有维护者一致同意（当前只有一位维护者，这条在出现第二位之后自动变成"全体一致"）。

**获得什么**

- 仓库写权限、合并权、发布权。
- 对"需要拍板"的条目有否决权，且必须书面写理由。
- 可以提名下一位维护者。
- `CONTRIBUTORS.md` 的 *Maintainer* 一节，且名字出现在 `package.json` 的 `maintainers` 里（加这一条需要一次 RFC 之外的普通 PR）。

**下一步怎么走**

维护者没有"下一级"。这一级的任务是让阶梯上的其它四级都有人站着——具体说：至少有一位 L3、一位 L4，否则你不算把项目交出去了。

---

## 评审 SLA

时间从"PR 打开或从 draft 转为 ready for review"算起，按北京时间工作日计。

| 场景 | 承诺 | 兑现方式 |
| --- | --- | --- |
| 任何新 PR / 新 issue 的**首次响应** | **48 小时内** | 一条实质回复：要改什么，或者明确说"我在 X 之前看不了" |
| **小 PR**（≤ 200 行改动，或纯文档、单文件、单 skill） | **72 小时内给结论** | 合并、或给出可执行的修改清单；不会无限期挂着 |
| 大 PR（驱动新增、内核改动） | 首次响应 48 小时内 + 分阶段评审 | 先给方向性意见，再逐轮收敛；你可以要求提前定评审轮次 |
| RFC | 收到后 7 天内进入 `Review` 或被打回 `Draft` | 打回必须写理由 |

维护者自己违反 SLA 时怎么办：在 issue 里 @ 一次，还没动静就直接开一个 issue 标题写 `[meta] SLA breach`。这条不用客气，它保护的是贡献者而不是维护者的面子。

---

## 我们不会做的事

写在这里，是为了让"被拒绝"变成可预期的事，而不是靠猜。

1. **不改协议语义来让某个功能变简单。** 想改 action / assertion / undo 的契约，走 RFC；夹带在功能 PR 里的，会被要求拆出去。
2. **不做只有 demo 效果的脚本。** 没有 `post` 断言、没有 `undo`、或者只在作者机器上跑过一次的东西，不进 `packages/skills/`。写进 `docs/recipes.md` 当示例可以，但会标明是示例。
3. **不为"方便"放宽能力 scope。** 一个 skill 因为它声明的能力不够而跑不动，正确做法是补声明并说明理由，不是把 scope 改成 `.*`。
4. **不偷偷改既有 skill 的预览快照。** 快照变了就是行为变了，PR 里必须解释。
5. **不为凑数合并 PR。** "测试全绿但没人需要"的改动会被关掉，并说明原因；这不针对人。
6. **不在贡献者之间搞人情排序。** 谁的意见被采纳，只看理由和证据，不看资历和关系。
7. **不因为一次争议移除人。** 只有行为准则（[CODE_OF_CONDUCT.md](../CODE_OF_CONDUCT.md)）里的那一类事才触发移除，技术分歧不触发。

## 现在就能开始的三件事

1. 打开 [GOOD-FIRST-ISSUES.zh-CN.md](GOOD-FIRST-ISSUES.zh-CN.md)，挑一个 **S**。
2. 跑 `node scripts/regress.ts`，让它全绿——这是你判断"我这台机器健康"的唯一标准。
3. 开 bounty issue 认领，48 小时内会有人回你。
