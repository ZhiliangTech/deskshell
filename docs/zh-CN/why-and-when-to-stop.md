写于 2026-11-01。不是对外材料，不给投资人、不发群里。目的是让下次迷茫时不用重新想一遍。

## 三个日期事实

| 事实 | 数字 | 含义 |
| --- | --- | --- |
| 建仓到现在的真实时长 | 2026-10-29 → 2026-11-01，**3 天** | 这不是"要不要坚持"的问题，沉没成本约等于零，是"要不要选"的问题 |

## 会被时间吃掉的（别再投入）

1. **消费者产品"AI 电脑管家"**。OS 厂商和模型厂商都在做入口，个人用户付费意愿低、支持成本高、出事就是数据事故。
2. **"会点鼠标"这件事本身**。computer-use 已经是模型厂商的基础能力，追它永远慢一个版本，而且追上了也没有差异。
3. **技能数量、平台数量、桌面壳**。都会被替代，不构成壁垒；先做这些只是让简历好看一点。
4. **480 小时里程碑表**（`goals/milestones.json`）。它度量投入，不度量价值。迷茫不是因为它不够细，正是因为它太细——把"我做了多久"当成了"我做的东西有用"。

## 可能留下的三样东西（按确定性从高到低）

### 1. 能力：确定性最高，已经基本落袋

撤销语义、效果凭据、摘要绑定的审批、崩溃窗口、SQLite 认领唯一性、Windows UIA/SendInput 真机坑、日志抗损。这些是"agent 真的动了用户的电脑之后怎么办"这一层的手艺，全世界实现过的人不多。

它不会因为项目失败而消失：换到任何 agent 平台团队、任何做端侧自动化的公司，这些都是直接能用的东西。**这是唯一确定有回报的一项，而且不需要项目成功。**

### 2. 基准：中等确定性，需要别人愿意跑

R0（失败后残渣率 / 可追溯率 / 可还原率）+ 15 次失败注入矩阵 + 反向对照（一个"只写不回滚"的实现会得 0 分）。基准比实现活得久，这是软件史的常态。

但现在的问题是：只有我们自己在跑。一个没人跑的基准等于没有基准。

### 3. 组件：最低确定性，但唯一可能被真实使用

把执行层做成能插进**别人** agent 的东西：MCP server / SDK，"给你的 computer-use agent 加一层可撤销、可审计的执行层"。

这是唯一现实的形态。因为换 agent 的成本极高（用户已经绑定了 Claude / Cursor / 自家 agent），而加一层安全网的成本很低。而"AI 把我东西搞坏了、我不知道它干了什么"是真实且普遍的痛。

## 唯一值得押的楔子

不是"用我们的 agent 干你的活"，是"**拦在你已经在用的 agent 和你的文件之间**"。

6 周验收（到 2026-12-15），三条都要有证据：

| 判据 | 证据形态 |
| --- | --- |
| 3 个真实任务在真实目录上跑完，每次都能逐字节撤销 | 三次 `journal` + 撤销前后目录哈希 |
| 1 个非本人跑通安装（不给文档，只给命令） | 对方的终端输出或录屏 |
| 1 条外部反馈能指出具体哪一步的 undo 救了他 | issue / 聊天记录原文 |

三条都做不到，就说明这条路没有需求，不用再自我说服。

## 止损条件（写下来才算数）

- **6 周内 0 外部使用** → 转"作品集路线"：停止加功能，把协议、R0、恢复机制写成 2 篇长文 + 1 段 15 分钟讲解，项目冻结在 0.x。桌面壳（M07）、Linux 控件层（M06）、技能库扩张全部砍掉。
- **出现 1–2 个真实用户** → 只做他们提的需求，砍掉其余一切"看起来完整"的工作。
- **任何时候** → 不为凑满 480 小时写代码。小时数是过程指标，项目需要的只有一条：有人真的在用它做一件他不敢交给普通 agent 做的事。

## 一句话

这个项目的价值不在"做出一个 OS"，在"证明 agent 的动作可以被约束、被验证、被撤回"。
把这句话变成别人愿意引用的一页纸（加一个能跑的命令），比再写五千行代码有用。

## 附：宏大目标逐条判断（2026-11 的判断，2027 年复核）

`PROJECT.md` 的愿景不是一个命题，是六条不同性质的命题混在一起。混在一起就没法判断，拆开就清楚了。

| # | 设想 | 判断 | 为什么 | 时间窗 |
| --- | --- | --- | --- | --- |
| A | 意图式交互取代以应用为中心的操作 | **部分成立，形态不同** | 意图入口会变多，但长在**应用内部**（IDE、浏览器、Office 各带自己的 agent），不是"一个 agent 接管整台电脑"。原因不是技术不够，是可靠性经济学：通用 agent 的错误率随任务步数上升，而"整机接管"要求它在**所有**应用上都不出错；平台方也有强动机把 agent 锁在自己的数据与商业模式里 | 已发生，2028 前定型为"多 agent + 协调层" |
| B | 本地模型成为个人计算的推理基座 | **不按"本地为主"实现** | 稳态是混合：本地跑路由、隐私敏感、低延迟的小任务，云端跑长上下文和强推理。同一代模型本地尺寸差 1–2 个数量级，而云端推理的单位成本还在快速下降——成本曲线站在云端一边 | 2028 年前不会反转 |
| C | 执行/权限/验证/恢复由系统层负责，模型不进内核 | **成立，且最确定** | 这是六条里唯一"需求与供给都成立"的：agent 动用户的文件，就必须有人负责记账、授权、回滚。差别只在**谁来做**——大概率是平台内置，而不是第三方 OS 运行时（中间件只在"应用极多且平台方不做"时才独立存在，参见浏览器 DOM、移动端权限模型） | 已在发生，2027 前后成为产品标配 |
| D | 语义资源视图（跨表示的对象身份、版本、约束） | **只在研究里成立，产品上会被绕过** | 这条的前提是"模型看不懂屏幕，所以要给它结构化对象"；而模型正在变得能看懂屏幕。价值随模型能力上升而下降，**除非**限定在高风险编辑（结构化文档、表格、代码）——那里需要字段级的精确恢复，语义身份仍然必要 | 作为论文 5 年内可立；作为产品卖点 5 年内不成立（除表格/文档垂直场景） |
| E | 效果凭据与选择性恢复 | **成立，需求侧最硬** | 换个说法就落地了：agent 干过的事必须能查、能撤、能定责。企业采购会把它变成合规与责任归属的硬门槛；消费者要等到第一次被 agent 搞坏东西 | 2027–2029 企业侧先起量 |
| F | 硬件成为本地智能体的载体 | **方向对，但不属于个人项目** | "常驻本地推理"会以 PC/NPU 内置的形式普及，这是确定的；但硬件是资本与渠道生意，个人/小团队无法参与，只能作为背景假设 | 已发生，与你无关 |

主观概率（不是预测，是用来校准自己的下注）：

- 2028 年前，"通用 agent 可靠完成跨应用任务"成为日常 → **30%**
- 每个主流 agent 平台都提供动作级审计与回滚 → **85%**
- 这个能力由**第三方协议**提供而不是平台内置 → **15%**
- "跨表示语义资源"成为产品级机制 → **10%**（作为研究被引用 → 40%）
- 个人计算围绕**本地模型**重组（而非云端） → **25%**（混合形态 → 70%）

### 这三条推论，比概率更重要

1. **宏大目标的作用是给岔路口一个方向，不是给今天打分。** 用它评价一个 3 天的仓库，得到的只能是"我做的没意义"——这个结论在任何时间点都成立，也任何时间点都没用。
2. **C 和 E 是你唯一能影响、且不依赖别人同意的部分。** A/B/D/F 由平台方、硬件周期和模型能力决定，你插不上手；只有"agent 的动作要可验证、可撤回"这一条，现在写代码就能推进。
3. **D 要降级。** 它值得写成研究笔记和 RFC，但不该出现在产品承诺、README 首屏或对外叙事里。把研究假设当卖点，是最容易在第一次真实对话里被戳穿的地方。
