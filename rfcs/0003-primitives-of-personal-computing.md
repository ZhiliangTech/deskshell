# RFC 0003 — 个人计算的四个原语：对象、效果、检查点、委托

- Status: Draft（设计命题，未经实验验证）
- Author: 根据维护者确认的方向（个人计算的形态）整理
- Created: 2026-11-01
- Protocol: Action v0 不变；本 RFC 只新增**可选侧车**（ObjectRef / EffectReceipt / CheckpointRef / Delegation），缺省关闭
- Related: [RFC 0001 — 本地智能体系统](0001-local-agent-system.md)、[RFC 0002 — 语义资源视图与效果凭据](0002-semantic-resources-and-effect-receipts.md)
- Evidence status: 尚无原型与对照数据。本文不主张首创，只主张"这四个原语必须同时存在，缺一个系统就退化"这一结构性判断，并给出可证伪的实验

## Motivation

今天的个人计算机有三个结构性缺陷，它们不是产品问题，是模型问题：

1. **没有时间。** 你无法问"我的电脑在 14:32 是什么状态"，也无法回到那一刻。备份是粗粒度的（按天），版本控制只覆盖代码，文档、照片、设置、应用状态都没有历史。
2. **没有因果。** 文件系统只记"现在是字节 X"，不记"谁改的、从哪个表示改的、依据什么"。于是任何自动化出事后，唯一可用的调查手段是人的记忆。
3. **语义住在应用里。** "这是一份 Q3 报告"这件事只存在于 Word 的窗口里。文件系统只看见字节，所以 agent 想理解你的电脑，只能去看屏幕——那不是因为它笨，而是**底座里没有语义**。

这三条合起来解释了一个现象：让 agent 操作电脑，最可靠的办法是模拟人（截图 + 点击），最不可靠的也是它。因为**投影被当成了本体**。

本 RFC 的命题是：**下一阶段的个人计算机，是一台带账本的状态机，加上若干可对账的投影。** 不是"更好的 agent"，也不是"agent 专用操作系统"，而是把底座补上缺的那三样。

## Proposal

### 四个原语

| 原语 | 一句话 | 缺了它会怎样 |
| --- | --- | --- |
| **Object** | 一个东西的身份，以及它在磁盘、应用缓冲、窗口、结构化视图里的多个投影 | 同一份文档被当成四个不同对象，agent 只能靠猜 |
| **Effect** | 一次变化的记录：谁、对哪个对象、改了哪一部分、前后是什么、依据什么 | 出事只能靠人回忆，无法选择性恢复 |
| **Checkpoint** | 一个**工作集**（不是整盘）的可分叉快照 | 没有时间维度，只有"现在的样子" |
| **Delegation** | 一份有作用域、预算、期限、例外、复议的授权 | 人只能在"完全信任"和"完全不给"之间二选一 |

四者必须同时存在，因为它们是彼此的坐标系：Effect 需要 Object 才有意义，Checkpoint 需要 Effect 才能解释差异，Delegation 需要 Effect 才能追责。

### 最小协议形状（全部可选，缺省关闭）

```ts
interface ObjectRef {
  id: string;                 // 稳定身份，跨改名/移动/重建
  version: string;            // 内容寻址：改了就是新版本
  projections: Projection[];  // 磁盘 / 应用缓冲 / 窗口 / 结构化视图
}
interface Projection {
  kind: "bytes" | "buffer" | "window" | "fields";
  locator: string;            // 路径、HWND+文档标识、字段路径
  digest: string;             // 用于检测投影之间是否分歧
  observedAt: number;
}

interface EffectReceipt {
  objectId: string;
  scope: string;              // 字段路径 / 字节区间 / 整个对象
  before: string;             // 版本或摘要
  after: string;
  origin: string;             // 哪个 agent、哪次委托、哪个动作
  evidence: string;           // 可复核的凭据（哈希、断言结果、独立重读）
}

interface CheckpointRef {
  workingSet: string;         // 明确列出范围，不做整盘快照
  id: string;
  createdAt: number;
  parent?: string;            // 可分叉 → 可以问"如果当时那样做会怎样"
}

interface Delegation {
  scope: string[];            // 允许触碰的对象/目录/应用
  budget?: { usd?: number; actions?: number };
  expiresAt?: number;
  exceptions: string[];       // 必须回来问人的情形
  appeal: string;             // 出了问题怎么复议（人工路径）
}
```

与 Action v0 的关系：**Action 是 Effect 的一种实现方式，不是替代品。** 现有技能不改也能跑；只有声明了 Object/Effect 侧车的技能才产生结构化凭据。

### 三条人类可见性要求（不可妥协）

1. **可读**：对象、效果、检查点、委托都必须有人能直接读的形态（文本/markdown），不能只存在于数据库。
2. **可审**：任何一次变化都要能回答"谁、依据什么、能不能退"。
3. **可导出**：全部能带走。记忆和授权不应被某个 agent 的实现格式锁死。

## 三个可证伪的实验

按风险从高到低排。**每个实验都必须能失败**，失败时给出"命题哪里错了"的结论。

### E1：语义底座够不够用（最高风险）

- **假设**：如果对象模型给出了身份、版本和结构化字段，"不给屏幕"的 agent 在文档编辑任务上的成功率不低于"截图 + 坐标"，且残留更低。
- **做法**：同一批 20 个文档编辑任务，两组执行（A：对象模型；B：截图 + 点击），同模型、同预算、同授权。
- **指标**：任务成功、误改对象、残留（失败后是否留下半成品）、token 成本。
- **判定**：A 的成功率低于 B 的 80%，或残留高于 B → **命题错**：语义底座不能替代感知，agent 仍需屏幕。此时应把研究重心移到"投影对账"而不是"语义视图"。
- **现在能否做**：能。Notepad 固定任务链已经能提供 buffer + 磁盘双投影。

### E2：投影分歧能不能被检测并安全处理

- **假设**：一个对象同时有磁盘版本和应用缓冲版本时，系统能检测分歧，并在不丢数据的前提下处理（合并或明确拒绝）。
- **做法**：打开文档 → 改磁盘 → 再改缓冲 → 让系统判定。抽样 20 次，含并发、崩溃、外部工具写入。
- **指标**：检测率、误判率（把一致判成分歧）、数据丢失次数（必须为 0）。
- **判定**：丢失次数 > 0 → 命题错：只能做"拒绝 + 人工裁决"，不能做自动合并。

### E3：选择性恢复在不覆盖人工修改的前提下成立

- **假设**：两个写入者改了同一文档的不同字段，系统能只撤回 agent 的字段，保留人工字段。
- **做法**：字段级效果凭据 + 三方合并；20 组，含同字段冲突、格式变化、重命名。
- **指标**：无冲突恢复成功率、冲突识别率、静默覆盖次数（必须为 0）。
- **判定**：静默覆盖 > 0 → 命题错：字段级恢复需要应用内协议支持，不能只在文件层做。

## Protocol diff

- 新增四个可选侧车类型；不修改 `spec/protocol-v0.json` 中任何既有字段。
- `protocol-freeze-test` 增加一条：**未声明侧车的技能，行为与 v0 完全一致**（兼容性是硬约束）。

## Migration

- 侧车缺省关闭；开启后只对显式声明的对象生效。
- 旧日志不含 EffectReceipt，恢复时退回"整对象"粒度，并如实标注粒度不足。

## Regression evidence

现有 72 项无桌面回归 + 新增 E1/E2/E3 脚本。在实验完成前，本 RFC 不产生任何"已完成"的结论。

## Alternatives

| 替代方案 | 为什么不够 |
| --- | --- |
| 整盘快照（时间机器式） | 成本随磁盘增长，且无法回答"哪个 agent 改的"；只能做时间，不能做因果 |
| 只做 CRDT / OT | 解决并发合并，不解决"谁授权、能否追责、能否只退回一部分"；也没有投影概念 |
| 只做屏幕操作（现状） | 最通用但残留最高，且无法解释因果；适合作为 E1 的对照组而不是终点 |
| 数据库中心化（一切进 DB） | 违背可读/可导出要求，且个人计算的历史教训是"应用死了数据就死了" |

## Rollback

关闭侧车即退回 v0：四个类型都是可选的，内核行为不变；已写入的 EffectReceipt 作为纯审计材料保留，不参与撤销决策。

## Open decisions

| 编号 | 待定 | 默认处理 |
| --- | --- | --- |
| O1 | 对象身份用内容寻址还是 UUID（改名/移动后是否应保持同一身份） | 先用"UUID + 版本内容寻址"的混合，实验后再定 |
| O2 | 应用缓冲如何接入（不依赖厂商配合的最小路径） | 先只支持能观测到缓冲的应用（Notepad 一类），其余降级为磁盘投影 |
| O3 | 检查点的存储成本与保留策略 | 按工作集 + 内容寻址去重，先测 1 万文件的工作集成本 |
| O4 | 委托的到期、复议与"人不在场"时的默认行为 | 默认到期即失效，异常一律回到人工，不做自动续期 |
