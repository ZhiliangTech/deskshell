# RFC 0002 — 语义资源视图与执行效果凭据

- Status: Draft
- Author: Codex，根据项目维护者确认的研究方向整理
- Created: 2026-10-31
- Protocol: Action v0 → v0；拟新增的 TaskView / EffectReceipt 协议独立版本管理
- Related: [RFC 0001 — 本地智能体系统技术路线与工程设计](0001-local-agent-system.md)、[模型后端配置](../docs/zh-CN/model-backends.md)、[首个真实应用](../docs/zh-CN/first-application.md)
- Research direction: 两个研究方向已获维护者确认；具体 schema、关联算法、恢复算法和实验阈值仍为 Draft
- Evidence status: 尚未实现研究原型，尚无性能或任务效果结论，不主张首创

## Motivation

RFC 0001 建立固定计划、可信授权、持久任务和恢复边界。它们是必要的工程基础，但没有直接回答两个问题：模型应该看到怎样的电脑资源世界，以及系统如何识别自己实际改变了什么。

第一类问题发生在规划时：用户要求修改一个已打开的文件，模型分别看到文件路径、窗口标题和控件树，却无法可靠判断它们是否代表同一个对象。文件被改名、窗口被重建、用户切换文档后，原来的文字描述仍可能看起来合理。仅增加工具数量或保存更长对话，不能自动解决对象对应与观察过期。

第二类问题发生在恢复时：agent 修改结构化文档的字段 A，用户随后修改独立字段 B。整份快照恢复会覆盖 B，整文件摘要保护则可能拒绝恢复 A。本项目需要研究在可证明的条件下只恢复 agent 的那部分改动，并保留用户之后的独立修改；同字段冲突和无法判定的效果必须另行处理。

本 RFC 确认以下研究问题，不预先承诺它们的答案：

1. 当前以同一云端 API/model、底层工具能力、权限和预算进行对照时，任务相关、具有稳定身份与版本的资源视图，能否提高经核验的任务成功率，或降低观察与推理成本？未来通过同一任务协议在本地模型上独立复验，云端服务端硬件不可控这一限制必须保留在结论中。
2. 可信执行端产生的字段级效果凭据与依赖记录，能否在不静默覆盖人工修改的前提下，提高无冲突情况下的恢复覆盖率？

### 已有思想与拟验证的贡献

AIOS 已研究面向 agent 的内核服务、资源隔离、调度、上下文与存储管理；因此“agent 操作系统”名称及运行时分层不能作为本项目的首创依据。[AIOS 原论文](https://arxiv.org/abs/2403.16971)

AgentOccam 已证明观察与动作空间的设计是值得研究的变量。本项目需进一步验证的是本地电脑中跨表示的资源身份、版本化任务视图及其更新机制，而不是声称首次为模型简化观察。[AgentOccam 原论文](https://arxiv.org/abs/2410.13825)

Temporal 的工程实践已有错误分类、补偿与故障注入等内容；持久执行和失败后补偿本身不是本项目的创新。本项目拟验证的是执行端如何生成可检查的细粒度效果记录，以及这些记录能否支持保留独立人工修改的恢复决策。[Temporal best practices](https://docs.temporal.io/best-practices)

稳定对象句柄、语义图谱、三方合并、事件溯源和补偿事务也提供了相关思路。是否构成新的机制贡献，必须经相关工作比较、原型与对照实验判断；目前只确认研究方向。

### 当前云端实验与未来本地复验

用户已明确修正实施顺序：长期仍发展本地智能体与本地模型，当前先使用真实云端 API 验证两项研究机制。本地电脑上的资源与执行仍由 Task Host 管理；推理放在云端不改变宿主授权、固定计划、凭据核验和恢复边界。云端实验只能支持其已测后端、任务和配置下的结论，不能证明小模型、本地离线推理或本地 RAM/VRAM 的收益。

云端适配器只发送宿主数据策略允许外发的任务上下文、资源属性与必要内容片段。读取授权不自动等于外发授权；各基线先经过相同的数据范围控制，再比较观察表示。恢复原像（preimage）、原始备份和宿主凭据不作为模型上下文或日志附件上传；必要任务内容由受限观察接口提供。API key 仅由受控网络客户端用于认证，不进入提示词、模型工具参数、实验导出或日志。截断、脱敏与被拒绝的外发请求需要记录其范围，模型不能扩大该范围。

每轮实验记录供应商、endpoint、请求 model/别名、服务返回的模型版本或标识、采样与推理参数、请求时间窗口、usage、计费信息和失败/重试。若供应商不允许固定底层版本，明确写“别名可变、底层版本不可固定”，不能把同一别名视为完全相同的模型快照。不可获得的版本、usage 或服务端配置标为未知，不填成零或假设不变；成本区分供应商实际账单与按注明时间的单价估算。

云端服务端硬件、调度和队列不受本项目控制。固定客户端硬件只能控制本机视图构建与执行成本，不能表述成“各组使用同一云端硬件”。未来本地复验另记录模型文件摘要、量化、后端版本、硬件、解码设置与资源占用，并独立报告，不与云端数据合并成小模型效果结论。

当前修订只记录设计与默认配置，没有发起真实 API 调用，没有发送任务数据或恢复材料，也没有产生模型性能测量。

### 已选真实应用与字段恢复边界

G4 的首个真实应用已选 Windows 记事本 Notepad；2026-10-31 的已安装版本观测为 `11.2607.14.0`。这只是安装状态证据，尚未验证启动协议、标签页/保存设置、UIA 对象身份、读取/写入/撤销和窗口重建行为。具体方案与后续证据集中在[首个真实应用](../docs/zh-CN/first-application.md)，运行实验时重新记录实际版本和设置。

字段级选择性恢复的主证明仍由结构化 JSON 与受控 UI fixture 提供。Notepad 用于验证真实应用的资源关联、观察过期、文档操作与可核查结果；不能把 JSON 字段凭据的结果推广成 Notepad 支持字段级、文本范围级或完整因果恢复。只有完成相应原语合同与实测后，才扩大恢复声明。

### 机制一：稳定身份与版本化任务视图

资源视图是经过授权的、面向当前任务的观察投影，不是整台电脑的完备真相，也不是授权凭据。可信 provider 负责观察与对象解析，视图构建器负责组织与裁剪；模型只消费视图并提出请求。

每个资源对象至少描述：provider、资源类型、稳定 ID、身份有效期、已观测版本、采集时间、属性、证据来源，以及该 provider 支持的操作。操作描述须分别表示“支持”“需要批准”“当前已获授权”，不能把显示出来的操作等同于已经可以执行。

身份与版本遵守以下规则：

- 路径、窗口标题、控件坐标是定位信息或显示信息，不是独立可信的稳定身份。资源 ID 由 provider 产生并由执行端解析，模型不能自造 ID 后要求访问任意路径。
- 文件改名或同卷移动能否保留身份由 provider 证明；复制、跨卷移动、删除重建和 ID 复用需要明确的新身份或有证据的转换关系。文件内容相同不等于同一对象。
- 文件、内存中的未保存文档、窗口和控件分别建模。它们可以有“由此打开”“显示此文档”等关系，不能因为标题相似而合并成一个对象。未保存文档和磁盘文件可以具有不同版本。
- 版本表示 provider 在明确观察范围内核验过的状态，不只是一枚时间戳。文件身份、内容、元数据，JSON 字段与 UI 属性可有不同版本粒度；具体编码待原型验证。
- `viewRevision` 表示视图的一次构建；它不替代每个资源的版本，也不保证之后执行时资源仍未变化。
- 无法获得稳定身份的资源必须标为临时或未确定；不能伪装成可跨会话安全复用的对象。

### 基于证据的关联与视图更新

MVP 优先使用第一方执行结果建立关系。例如，执行端打开某个文件后，记录文件身份、创建或绑定的文档实例及窗口实例。后续观察可以核验或撤销该关联。仅根据标题、内容相似度或模型推断建立的关系只能是候选。

关系至少区分 `verified`、`candidate`、`stale`，并引用可查的观察或执行凭据。模型可提议候选关系；只有可信 resolver 在其声明的证据条件成立时才能将其用于写操作定位。存在多个候选、身份矛盾或证据不足时，补充受限观察或请求用户选择，不能用模型 confidence 替代对象核验。

第一版视图选择使用确定性规则：用户选定资源、任务参数引用的资源、必要依赖和已知冲突对象。先不要求训练一个相关性模型。被隐藏或截断的内容须留下范围与截断信息；“视图中未展示”不得解释为“系统中不存在”。模型可以申请扩展观察，但仍受原有权限和预算约束。

已验证的效果凭据可以触发局部视图失效或增量刷新。外部编辑、窗口重建、权限变化及 provider 重启同样触发失效。事件通知可以用于发现变化，但不能替代执行前的对象与版本核验。

过期视图下的写提案必须返回明确的 stale/ambiguous 结果。刷新导致目标、动作、资源范围或用户验收条件变化时，重新生成 PreparedPlan 和摘要，遵循 RFC 0001 的重新批准规则。不能在后台把旧 ID 静默换成“看起来类似”的新对象。

### 模型提案与可信执行边界

模型提出的请求形如“对资源 R、基于版本 V，调用已登记操作 O，参数为 P”。请求可携带视图引用和解释，但不能携带宿主授权、任意可执行代码、可直接访问系统的句柄或自行生成的成功证明。

可信端依次核验运行时 schema、资源归属与身份、操作版本、参数、读取与修改权限、观察版本和预算，再构造 RFC 0001 的固定计划。最终执行仍依据宿主保存的 planId/digest/approval；每个计划只能认领一次执行实例。

模型可提出 `goalCriteria`，但用户目标摘要和可信目标验证器仍由宿主维护，并绑定计划摘要。动作调用成功、视图被更新和任务目标成功是三个不同事实。文件正文、窗口文字及工具返回中的指令始终是外部数据，不能修改上述规则。

### 机制二：执行端产生的效果凭据

EffectReceipt 记录一次已支持原语在声明范围内的观察结果。其可信性来自受信 provider 的代码路径、执行前后的核验与受控存储，而不是来自对象名、哈希、签名字段或模型声称“已完成”。它不意味着已经捕获该操作在整个操作系统中的所有副作用。

拟记录的内容包括：

| 字段组 | 含义 |
| --- | --- |
| 归属 | taskId、planId、stepId、attemptId、provider 与实现版本 |
| 操作 | 已登记原语 ID/版本、规范化参数摘要、批准效果范围 |
| 身份与版本 | 目标资源身份，执行前版本、观察到的执行后版本 |
| 读取与修改 | 实际获准读取集合、受验证的写集合、字段或区域、已知变化 |
| 证据 | 前后观察引用、验证器 ID/版本、验证结果与证据覆盖范围 |
| 恢复材料 | 原始字节/原值的私有存储引用、完整性摘要、保留期限 |
| 效果分类 | 可精确恢复、可补偿、不可逆；与结果是否未知分别表达 |
| 恢复条件 | 对象身份、当前值/版本、依赖、权限等条件，以及已登记的逆操作 |
| 限制 | 未观测区域、外部效果、无法归因的变化、不支持的恢复语义 |

执行端先保存恢复材料，再持久化可引用这些材料的执行意图；动作发生后记录观察和验证事件。只有核验完成的记录可以标记相应效果已验证。数据库、备份和外部资源不能组成统一原子事务；缺少完整凭据不能证明动作没有发生。

凭据由宿主拥有的存储维护，skill/model 不得直接写入或修改它。preimage 不默认进入模型上下文；目录 ACL、留存和删除策略沿用 RFC 0001 的宿主存储边界。操作未获准读取的内容，不能以“制作恢复材料”为由偷偷读取。

### 读写依赖与选择性恢复

读集合来自经 broker 提供的观察和原语实际检查，不以模型自报为唯一依据。无法证明最小读取集合时采用保守的范围。写集合由已登记原语与观察共同确定；对任意 UI 点击不能仅靠前后屏幕差异宣称完整写集合或因果归属。

当后一步读取了前一步产生的资源版本，或两步修改重叠区域时，记录相应依赖与顺序约束。依赖关系只覆盖经过运行时观测的访问；对其他应用的隐藏读取不作完备性保证。不能仅根据时间先后推断因果。

恢复先产生候选逆操作，再核验：对象仍是原对象、修改区域仍满足该逆操作的条件、依赖不会被未授权破坏、恢复材料可用、当前权限允许。成功恢复的字段或区域另记凭据；剩余冲突和未知部分保持可见。跨任务消费者存在时，不自动级联撤销其他任务；提示依赖和受影响结果，由宿主策略或用户作出新决定。

MVP 从有限原语开始：按身份移动文件、修改 JSON 顶层字段、设置受控 UI 字段。JSON 嵌套对象、数组索引移动、重复键、富文本和任意二进制内容不默认获得字段级恢复能力；不支持的结构须拒绝该原语，或明确采用整文档保守模式。字段/祖先区域重叠视为冲突。具体 JSON 解析与序列化约束需在实现前固定。

#### 字段 A/B 的验收例子

初始文档为 `{"A":"old","B":"old"}`。agent 经批准把 A 改为 `"agent"`，之后用户把 B 改为 `"human"`。如果对象与证据链仍满足字段逆操作的条件，恢复结果应为 `{"A":"old","B":"human"}`。若用户改的是 A，或该文档被另一个文件替换，则报告冲突，不覆盖现场。

这项例子证明的是在定义范围内保留独立字段的当前值，不自动承诺保留所有 JSON 排版字节。原始字节用于无冲突的精确恢复；存在外部修改时，是否承诺字段语义、格式或字节级保留必须分别声明和测试。不得把“语义相同”报告成“逐字节相同”。

当前值等于 agent 写入值，也不足以证明中间没有人工修改后又改回的 ABA 情况。凭据须说明是否有完整版本沿革、是否漏过外部变化。没有足够证据满足声明的恢复条件时，进入 conflict/unknown，不能声称掌握了真实修改者。受控 fixture 可以提供完整变更序列；真实应用是否具有同等证据必须另验。

### 并发、崩溃与未知效果

运行时资源锁约束经过宿主的任务，不能阻止其他应用或人工编辑。锁范围要与对象身份及写区域一致，不能只比较当前显示路径；模型决定动作和恢复算法生成逆操作后，执行端仍需重新核验实际对象状态。

无可依赖的条件写入、稳定句柄或外部编辑协调机制时，读后再写之间仍可能发生竞态。MVP 只在明确协调的 fixture 与声明的文件并发假设下验证；不能据此宣称抵御任意本地敌对进程。真实文件 provider 的句柄、原子替换及冲突检测能力需作为单独验收项。

崩溃发生在外部效果与持久记录之间时，采用 RFC 0001 的 `uncertain/needs_attention` 处理。重新观察只能支持可证明的补记或有条件恢复，不能把截图相似、值相等或缺少日志作为自动重放的理由。补偿自身同样可能中断，需持久记录意图与结果；重复恢复请求不得重复产生未经核验的副作用。

对不确定的执行结果不构造虚假的“已验证”凭据，对不确定的恢复不标记完整回滚。受控字段恢复成功不代表同一次 GUI 操作触发的联网、保存钩子或其他外部效果也已恢复。

### 原型结构与推进顺序（Draft）

建议先沿 RFC 0001 现有模块边界放置原型，以下路径不是已建目录或已决定公共 API：

| 候选位置 | 原型责任 |
| --- | --- |
| `packages/runtime/resources/` | 资源注册、身份解析、观察版本与证据关系 |
| `packages/runtime/views/` | 授权范围内的任务视图、裁剪、失效和增量刷新 |
| `packages/runtime/effects/` | 效果凭据校验、读写依赖、逆操作候选与冲突判断 |
| `packages/drivers/` | 文件/JSON/受控 UI provider，产生实际观察与原语执行证据 |
| `packages/storage/` | 沿用 TaskStore，保存资源引用、观察、事件和恢复材料索引 |
| `scripts/research/` | 版本化夹具、扰动、独立验证器和对照实验入口 |

先用确定性原语和受控数据证明身份、失效、凭据和条件恢复；再加入同一真实云端 API/model 的对照；随后按首个应用方案验证已选的 Notepad，未来使用同一任务协议进行本地模型复验。可与 RFC 0001 的观察协议设计并行，但模型写入依赖 G1 授权与固定计划，崩溃恢复结论依赖 G2 持久状态。不要为实验绕过这两个入口。

## Protocol diff

本 RFC 不修改 `spec/protocol-v0.json`、现有 Action/Skill v0 或运行时代码。以下是新任务层的数据流差异和结构草案，不是已冻结协议，也不是可立即调用的 SDK。

```diff
- 模型看到分散的路径、标题、控件树；每次重新推断目标与可操作性
- skill 提供 undo；日志主要记录步骤状态和逆动作
+ 模型看到有来源、身份、版本和操作条件的 TaskView
+ 模型提交资源/版本/操作提案；可信端转为 RFC 0001 PreparedPlan
+ 执行端产生作用范围明确的 EffectReceipt；恢复依据凭据和当前状态判定
```

```ts
// 示意类型；JsonValue、ActionProposal 等公共类型尚待正式 schema 定义。
type IdentityState = "verified" | "ephemeral" | "ambiguous";
type RecoveryClass = "exact" | "compensatable" | "irreversible";

interface ResourceRef {
  providerId: string;
  resourceId: string;
  identityEpoch: string; // 防止会话结束或底层对象 ID 复用后误绑定
}

interface ResourceObservation {
  ref: ResourceRef;
  identity: IdentityState;
  version: string;
  observedAt: number;
  properties: Record<string, JsonValue>;
  evidenceRefs: string[];
  operations: Array<{
    operationId: string;
    operationVersion: string;
    authorization: "granted" | "approval_required" | "denied";
  }>;
  completeness: { scope: string; truncated: boolean };
}

interface TaskView {
  formatVersion: "1-draft";
  taskId: string;
  viewId: string;
  viewRevision: number;
  resources: ResourceObservation[];
  relations: Array<{
    from: ResourceRef;
    to: ResourceRef;
    kind: string;
    status: "verified" | "candidate" | "stale";
    evidenceRefs: string[];
  }>;
  omittedScope: string[];
}

interface ResourceActionProposal {
  viewId: string;
  viewRevision: number;
  target: ResourceRef;
  expectedVersion: string;
  operationId: string;
  operationVersion: string;
  args: JsonValue;
}

interface ResourceRegion {
  resource: ResourceRef;
  selector: { kind: "whole" } | { kind: "json-field"; key: string }
    | { kind: "ui-property"; property: string };
  observedVersion: string;
}

interface EffectReceipt {
  formatVersion: "1-draft";
  receiptId: string;
  taskId: string;
  planId: string;
  stepId: string;
  attemptId: string;
  producer: { providerId: string; implementationVersion: string };
  operation: { id: string; version: string; argsDigest: string };
  readSet: ResourceRegion[];
  writeSet: ResourceRegion[];
  beforeEvidenceRefs: string[];
  afterEvidenceRefs: string[];
  outcome: "not_applied" | "applied" | "unknown";
  verification: { verifierId: string; version: string; status: "verified" | "failed" | "incomplete" };
  recovery: {
    class: RecoveryClass;
    preimageRefs: string[];
    inverseOperationId?: string; // 登记的操作，不接受可执行函数或脚本文本
    conditionRefs: string[];
  };
  dependencyReceiptIds: string[];
  limitations: string[];
}
```

`ResourceActionProposal` 是待审核输入，不是执行许可。可信端规范化提案、解析当前对象并生成固定计划，资源/操作/版本等关键字段纳入计划摘要。可显示的操作列表也会过期，执行前重新检查授权和 provider 能力。

EffectReceipt 的实际修改区域、前后版本、证据、条件和时间顺序必须由运行时 schema 与注册原语合同完整定义。示例中的引用不可任意指向用户可写文件；宿主验证引用归属和材料完整性。记录修订采用事件追加或可追溯版本，不能让模型重写历史记录以制造“恢复成功”。

字段级恢复属于新增原语合同；旧 `fs.restore` 不会因为读取到这份 RFC 就获得字段合并语义。实现中如需改变 v0 动作或断言，另行提出明确协议变更。

## Migration

- 现有 skill：继续使用 v0 受信路径。研究入口只接入有明确原语合同的第一方 provider；逐个迁移观察与动作描述，不自动推断旧 skill 的读写集合。
- 既有 JSONL：保留旧读取/展示能力。旧日志中的 undo/hash 不自动转成完整 EffectReceipt；没有前置材料、身份或执行中记录的任务不得追溯认证为可选择性恢复。
- RFC 0001 新任务：PreparedPlan 和审批仍是唯一写入入口。视图可以在 prepare 前生成；计划准备后视图刷新不修改已批准计划。恢复由宿主沿既定批准策略核验；扩大范围或连带影响其他任务时产生新方案和授权。
- 存储：初期使用实验命名空间和独立 schema 版本，恢复材料位于宿主私有存储。导入若被需要，记录来源摘要并保证幂等；当前没有迁移脚本。
- 运行时依赖与冻结协议：本文不新增依赖，不改冻结清单，不切换生产执行路径。具体存储绑定、原生句柄支持与第三方依赖另按 RFC 0001 和仓库流程决策。

### 实验一：语义资源视图

当前各组使用同一供应商/API endpoint、请求 model/别名、采样与推理设置、底层工具词汇和原语能力、权限及外发数据范围，以及相同调用/重规划/token/时限/费用预算。不得为某组单独启用更强模型、不同推理等级或额外工具。模型无法固定底层版本时注明这一限制；配置记录遵循前述云端实验要求。

各组使用相同任务、初始状态、扰动时间表和独立目标验证器，在相近时间窗口内按任务配对、随机交错运行，并记录顺序、种子、请求时间及服务返回的版本信息。这样减少服务漂移的混杂，不能保证消除未知模型更新、排队或硬件变化；发现可见版本切换、限流或服务异常时分段报告并预先规定重跑规则，不择优保留请求。

客户端环境固定并记录，其 CPU/内存与耗时只用于本地视图和执行开销。端到端 API 延迟包含网络与服务调度，服务端冷启动无法观察时不得虚构该分组；客户端冷/热运行、缓存命中与服务端返回的 usage 如可获得则分别报告。上下文裁剪和数据策略造成的截断也记入报告，不能给某组隐藏增加预算。未来本地复验再固定模型文件、量化、推理后端及实际硬件，单独比较本地结果。

三个主要基线为：

1. 原始观察：文件清单、JSON 内容及 UIA/fixture 数据，使用相同原语工具。
2. 过滤观察：在相同原始数据上做任务相关裁剪，不增加跨表示稳定身份、关系和版本视图。
3. 完整语义视图：使用本文机制，仍调用相同原语；不能让这一组拥有高层操作而让基线只点坐标。

消融分别去掉跨表示身份关联、版本提示、操作可用性描述，以及把增量更新换成全量刷新。所有组的真实授权与执行安全检查保持相同；消融只改变模型获得的表示，不通过放松权限制造成功率差异。专门报告“只过滤”已能解释多少收益。

默认先做文件选择/整理、JSON 字段修改、文档打开/保存、窗口重建四类任务。扰动包括同名对象、相似标题、路径改名、目标替换、人工独立修改、同字段修改、视图过期、截断以及数据中的恶意指令。具体案例数量与每例重复次数在云端配置、费用预算和客户端环境可用后预登记，当前不设已完成的规模数字。Notepad 真实应用任务与受控 UI 任务分组记录，应用已选不代表对应能力已通过。

主要指标为独立验证的目标成功率、错误对象操作率、stale/ambiguous 处理正确率、API 报告的 usage/费用、观察调用数、端到端墙钟延迟及本地视图构建成本。token 细分和缓存信息按供应商实际可用字段记录，跨供应商计数不默认等价。完整成功、部分完成、合理拒绝、无必要拒绝、需人工处理和误报完成分别统计；拒绝不计作目标成功。报告分子/分母、逐任务结果、重复运行离散程度和配对差异，效果未显著时不得只挑有利子集。

### 实验二：效果凭据与恢复

使用相同初始数据、前向修改、人工扰动与恢复目标，比较：

1. 整份快照恢复，仅在隔离夹具中运行可能覆盖人工修改的对照。
2. 整文件摘要保护：当前内容变化则拒绝整步恢复，代表现有保守策略。
3. 字段凭据与条件逆操作：根据本文身份、区域、依赖和恢复条件恢复可证明安全的部分。

这项主实验先使用确定性文件/JSON/受控 UI 原语，不依赖云端模型判断恢复成功。若增加由模型触发前向任务的端到端实验，三组继续共享同一 API/model 与预算；恢复器和独立验证器仍使用相同证据规则。Notepad 的恢复能力只按已单独验证的原语报告，不能承接字段恢复实验的结论。

基础案例包括前述 A/B 独立修改、A 同字段冲突、JSON 不支持结构、文件身份替换、移动后编辑、跨步/跨任务依赖、ABA、漏观测，以及恢复过程中再次被修改。可信 fixture 的完整时间线只供评估器判定真值；不能把评估器的隐藏标签提供给被测恢复器。恢复器只能使用其实际采集的观察和凭据。

在意图落盘、原始材料保存、外部效果发生、结果落盘、补偿开始和补偿结果落盘等边界注入进程终止。必须分别判断“未执行”“已验证”“已知冲突/残留”“结果未知”，禁止把没有日志当作没执行。

指标包括人工改动静默丢失次数、已知无冲突案例的恢复覆盖率、冲突识别、错误恢复/错误拒绝、字段语义与字节保留、依赖处理正确性、未知状态报告，以及凭据采集/存储/恢复成本。无冲突分母由独立 fixture 合同与真值定义，不能由被测实现自己挑选；另报全体任务的恢复结果。

字段恢复率提高而人工数据丢失也提高，不能宣称机制成功。受控测试中的零次违规只说明该测试集未发现违规，不构成任意应用或并发环境下的证明。

### 进入后续阶段的条件

先通过已定义身份、授权、冲突与记账不变量；发生静默覆盖、错误对象写入或伪造成功记录时，阻止扩大原型范围。再看任务成功、恢复覆盖和成本是否相对于基线有可重复收益。数量化收益阈值、样本量、置信区间方法与允许的成本开销，在云端配置、费用预算、客户端环境和试跑估计明确后预登记，并在保留测试集上评估；未来本地复验另定硬件与性能阈值。

若完整视图不优于简单过滤，应保留较简单方案；若字段恢复收益不足或证据采集代价过高，应保持整资源保守恢复。真实应用结果单列，不与 Mock、受控 UI、合理拒绝合成一个百分比。

## Alternatives

1. 只增加模型上下文或截图频率：保留为对照思路，不作为主机制；它增加观察量，但没有直接建立对象身份、版本与跨表示关系。
2. 立即建立全电脑知识图谱：暂不采用；资源覆盖与关联错误会先于实验收益膨胀。先做任务范围内的小视图，允许显式不完整。
3. 仅依赖 skill 自报 undo、幂等与副作用标签：不作为新机制的依据；这些是提案，需要执行端凭据和当前条件核验。
4. 所有冲突一律恢复整个快照：不作为产品默认；会覆盖任务之后的独立人工修改。仅在隔离实验中作对照。
5. 把每次 GUI 操作前后差异都视为完整因果证据：不采用；应用内部、后台与网络副作用可能不可见，时间相邻也不等于由本动作造成。
6. 先实现通用自动合并和任意应用恢复：暂不采用；从少量有明确逆操作条件的原语验证，避免把不可证明的恢复包装成通用保证。

## Rollback

设计阶段只维护本文，不改变运行时行为。实现时以实验配置与独立存储版本引入；关闭语义视图后可退回受限原始观察，但仍通过 RFC 0001 的固定计划和授权入口，不退回模型直写。关闭或替换云端适配器不扩大外发权限，也不自动切换到另一供应商；后端变更另记配置与独立实验批次。

关闭选择性恢复时，对尚未处理的凭据采用只读展示和保守冲突判断；不得因为新版算法停用就将未知结果标为成功，或自动用整文件快照覆盖现场。保留原始事件和恢复材料，旧版本不理解的记录保持只读。

发现身份错配、静默覆盖或凭据错误，先停止相关 provider 接收写入，保全现场和证据，再决定针对哪些已知任务修复。回滚软件版本不等于撤销已经发生的文件、UI 或外部效果。
